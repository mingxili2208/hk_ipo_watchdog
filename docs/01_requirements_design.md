# 01. 需求设计文档：HK IPO Watchdog

## 1. 项目背景

港股打新信息分散在多个渠道，包括 HKEX / HKEXnews、券商 App、财经网站、暗盘报价页面、新闻公告等。人工跟踪存在以下问题：

1. 新股招股、截止认购、配发结果、暗盘表现等时间点容易遗漏；
2. 不同来源字段不统一，需要反复手动比对；
3. 每只新股都要人工判断是否符合个人策略，效率低；
4. 配发结果公告、招股书、财务数据阅读成本高；
5. 传统提醒工具只提醒时间，不会说明“为什么值得关注”。

因此，需要构建一个个人使用的港股打新监控系统。

## 2. 项目目标

系统目标是构建一个 **港股 IPO / 打新监控、筛选、摘要和推送系统**。

核心能力：

1. 自动抓取港股 IPO 相关信息；
2. 自动识别新股状态变化；
3. 根据用户自定义策略筛选；
4. 对符合规则的新股进行打分；
5. 调用 LLM 生成简洁摘要；
6. 推送到用户指定渠道；
7. 存储历史记录，为后续复盘和回测提供基础。

## 3. 业务边界

### 3.1 系统应该做什么

系统应支持：

- 监控港股新股日历；
- 监控招股开始、招股截止、公布配发结果、上市日、暗盘表现；
- 解析新股基础信息及来自官方招股章程的主营业务短摘要；
- 解析配发结果；
- 解析或抓取暗盘涨跌幅；
- 根据策略打分；
- 生成中文摘要；
- 发送实时提醒；
- 生成每日汇总；
- 保存抓取历史和推送历史；
- 支持策略配置文件修改。

### 3.2 系统不应该做什么

系统不应：

- 自动下单；
- 自动申购；
- 自动卖出；
- 代替用户做投资决策；
- 绕过券商或数据商权限限制；
- 对非公开数据进行抓取；
- 将模型输出直接作为投资建议。

## 4. 用户角色

### 4.1 个人用户

主要用户是一个关注港股打新的个人投资者。

需求：

- 想知道今天有哪些新股可以申购；
- 想知道哪些新股符合自己的低入场费 / 高热度 / 暗盘强势策略；
- 想在配发结果公布时收到提醒；
- 想在暗盘明显上涨或下跌时收到提醒；
- 想每天收到一份摘要。

### 4.2 系统维护者

通常也是用户本人。

需求：

- 能修改数据源配置；
- 能修改策略规则；
- 能查看日志；
- 能重新跑某个数据源；
- 能手动触发日报；
- 能查看历史推送记录。

## 5. 核心使用场景

### 场景 1：发现新股招股

当系统发现新股开始招股时：

1. 抓取 IPO 日历；
2. 发现数据库中不存在该股票；
3. 写入新股基础信息；
4. 根据基础规则判断是否需要推送；
5. 如果符合观察条件，则生成摘要；
6. 发送“新股招股提醒”。

### 场景 2：认购截止提醒

当某只 IPO 将在 24 小时内截止认购：

1. 调度器扫描所有招股中的 IPO；
2. 判断 `close_date - now <= 24h`；
3. 检查是否已推送过截止提醒；
4. 如果没有，则推送“认购即将截止提醒”。

### 场景 3：配发结果公布

当系统发现某只 IPO 发布配发结果：

1. 抓取 HKEXnews 或其他公告来源；
2. 识别配发结果公告；
3. 解析发售价、超购倍数、一手中签率、回拨比例等；
4. 更新 IPO 数据；
5. 重新计算策略得分；
6. 使用 LLM 生成配发结果摘要；
7. 推送“配发结果提醒”。

### 场景 4：暗盘异动

当暗盘价格出现显著变化：

1. 在暗盘交易窗口内每 5 分钟抓取暗盘数据；
2. 计算暗盘涨跌幅；
3. 判断是否超过策略阈值；
4. 如果触发阈值，推送“暗盘异动提醒”。

### 场景 5：每日汇总

每天固定时间：

1. 汇总当日新股、配发结果、暗盘变化；
2. 生成简洁日报；
3. 推送给用户；
4. 保存日报内容。

## 6. 功能需求

## 6.1 数据采集模块

### FR-001：IPO 日历采集

系统应能采集港股 IPO 日历信息。

字段包括：

- 股票代码；
- 股票名称；
- 市场板块；
- 行业；
- 招股开始日期；
- 招股截止日期；
- 上市日期；
- 招股价区间；
- 每手股数；
- 入场费；
- 保荐人；
- 数据来源；
- 来源链接。

优先数据源：

1. HKEX / HKEXnews；
2. AAStocks IPO；
3. Futu OpenAPI；
4. 其他可配置来源。

### FR-002：公告采集

系统应能采集 IPO 相关公告。

公告类型包括：

- 招股书；
- 聆讯后资料集；
- 招股公告；
- 配发结果；
- 稳定价格行动公告；
- 上市文件；
- 其他补充公告。

### FR-003：配发结果采集

系统应能识别并解析配发结果。

字段包括：

- 最终发售价；
- 香港公开发售认购倍数；
- 国际配售认购倍数；
- 一手中签率；
- 回拨比例；
- 甲乙组分配；
- 基石投资者；
- 配售集中度；
- 预计集资额；
- 上市日期。

### FR-004：暗盘数据采集

系统应能采集暗盘数据。

字段包括：

- 暗盘价格；
- 暗盘涨跌幅；
- 暗盘成交额；
- 更新时间；
- 来源券商；
- 数据来源链接。

注意：

- 暗盘来源通常不是 HKEX 正式市场；
- 不同券商暗盘数据可能不同；
- 系统应保留来源字段，避免混淆。

## 6.2 数据标准化模块

### FR-005：标准 IPO 对象

系统应将不同来源数据统一转换为 `IPOItem`。

标准字段见 `05_api_interface_spec.md`。

### FR-006：字段归一化

系统应处理：

- 股票代码格式，如 `3888`、`03888`、`HK.03888`；
- 日期格式；
- 货币格式；
- 百分比格式；
- 中英文名称；
- 行业名称；
- 保荐人名称。

### FR-007：数据冲突处理

当多个来源字段不一致时：

1. 以官方公告来源优先；
2. 保留所有来源原始字段；
3. 标记冲突字段；
4. 在摘要中提示“多源数据存在差异”。

## 6.3 去重和状态管理模块

### FR-008：去重

系统应避免重复推送。

去重维度：

- 股票代码；
- 公告类型；
- 公告链接；
- 发布时间；
- 推送类型。

### FR-009：状态跟踪

系统应跟踪 IPO 生命周期：

```text
planned
  ↓
hearing_passed
  ↓
subscription_open
  ↓
subscription_closed
  ↓
allotment_result_published
  ↓
grey_market_trading
  ↓
listed
  ↓
archived
```

### FR-010：事件记录

所有重要状态变化应保存为事件：

- 新 IPO 发现；
- 招股开始；
- 招股截止；
- 配发结果公布；
- 暗盘异动；
- 上市日；
- 数据冲突；
- 推送成功；
- 推送失败。

## 6.4 策略筛选模块

### FR-011：用户策略配置

用户应能通过 YAML 文件配置策略。

配置项包括：

- 最大入场费；
- 最小市值；
- 允许行业；
- 排除行业；
- 保荐人白名单；
- 保荐人黑名单；
- 最低公开认购倍数；
- 最低暗盘涨幅；
- 最低综合得分；
- 推送等级阈值。

### FR-012：规则筛选

系统应先使用硬规则筛选，不应直接依赖 LLM 判断。

例如：

- 入场费小于 5,000 港币；
- 公开发售超购大于 20 倍；
- 暗盘涨幅大于 5%；
- 一手中签率大于 5%；
- 保荐人不在黑名单中。

### FR-013：综合评分

系统应根据多个维度计算分数：

| 模块 | 建议权重 |
|---|---:|
| 基本面 | 30 |
| 热度 | 20 |
| 中签结构 | 15 |
| 暗盘表现 | 20 |
| 保荐人 / 股东背景 | 10 |
| 风险扣分 | -5 到 -30 |

### FR-014：分级推送

系统应支持四级提醒：

| 等级 | 含义 | 行为 |
|---|---|---|
| Level 1 | 普通记录 | 只入库 |
| Level 2 | 观察提醒 | 低频推送 |
| Level 3 | 重点提醒 | 立即推送 |
| Level 4 | 紧急提醒 | 立即推送并标记 urgent |

## 6.5 LLM 摘要模块

### FR-015：摘要生成

系统应调用 LLM 生成中文摘要。

摘要包括：

- 一句话结论；
- 核心信息；
- 触发策略；
- 风险点；
- 建议关注时间点；
- 数据来源提醒。

### FR-016：结构化输出

LLM 输出必须是 JSON，不允许只输出自然语言。

示例：

```json
{
  "title": "新股打新提醒：XXXX",
  "summary": "该新股入场费较低，当前符合观察条件。",
  "key_points": [],
  "risks": [],
  "trigger_reasons": [],
  "suggested_action": "等待配发结果或暗盘表现",
  "confidence": "medium"
}
```

### FR-017：模型可替换

系统应支持不同模型供应商：

- OpenAI；
- DeepSeek；
- Gemini；
- Claude；
- Qwen；
- 本地模型。

模型供应商应通过配置切换。

## 6.6 推送模块

### FR-018：Telegram 推送

系统应支持 Telegram Bot 推送。

配置项：

- Bot Token；
- Chat ID；
- 是否启用；
- 推送等级阈值。

### FR-019：邮件推送

系统应支持邮件推送。

配置项：

- SMTP Host；
- SMTP Port；
- Username；
- Password；
- Receiver；
- TLS/SSL。

### FR-020：Bark / Server 酱推送

系统应支持轻量通知渠道。

### FR-021：每日汇总

系统应在指定时间生成每日摘要。

内容包括：

- 今日新股；
- 今日配发；
- 今日暗盘；
- 明日截止认购；
- 明日上市；
- 重点关注列表。

## 6.7 存储模块

### FR-022：数据库存储

MVP 使用 SQLite。

后续可升级 PostgreSQL。

核心表：

- `ipo_items`;
- `ipo_events`;
- `announcements`;
- `grey_market_quotes`;
- `strategy_scores`;
- `notifications`;
- `llm_summaries`.

### FR-023：原始数据保存

系统应保存部分原始数据。

包括：

- 原始 HTML；
- 原始 JSON；
- 原始 PDF 链接；
- 解析后的中间结果。

## 7. 非功能需求

### NFR-001：可维护性

- 模块边界清晰；
- 数据源采集器可单独替换；
- 策略规则可配置；
- 推送渠道可扩展；
- LLM Provider 可替换。

### NFR-002：可靠性

- 数据源失败不能导致整个系统崩溃；
- 单个任务失败要记录日志；
- 推送失败要重试；
- LLM 失败时仍应保留规则判断结果；
- 页面结构变化时应产生错误事件。

### NFR-003：实时性

建议频率：

| 任务 | 频率 |
|---|---|
| IPO 日历 | 每 10-15 分钟 |
| HKEX 公告 | 每 5 分钟 |
| 配发结果 | 每 5 分钟 |
| 暗盘 | 交易窗口内每 5 分钟 |
| 日报 | 每天 21:30 |

### NFR-004：安全性

- API Key 不得写死在代码中；
- 使用 `.env` 管理密钥；
- 日志不得输出完整密钥；
- 推送内容不得包含账户敏感信息；
- 数据库文件应定期备份。

### NFR-005：合规性

- 遵守数据源 robots / API 使用规则；
- 不高频恶意请求；
- 不绕过登录或付费权限；
- 不提供自动交易功能；
- 推送内容应避免“确定性收益”表述。

## 8. 验收标准

MVP 验收标准：

1. 能成功抓取 IPO 日历；
2. 能将 IPO 标准化存入数据库；
3. 能根据 `strategy.yaml` 计算分数；
4. 能识别新 IPO 并推送；
5. 能识别认购截止提醒；
6. 能生成 LLM 摘要；
7. 能发送 Telegram 通知；
8. 能记录推送历史，避免重复推送；
9. 能生成每日汇总；
10. 能通过 Docker 启动。
